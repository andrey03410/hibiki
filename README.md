# Hibiki · 響き

Личная медиатека с составными плейлистами и управлением через внешних ИИ-агентов.
Музыка и видео живут в одной библиотеке и могут играть в одной очереди.

## Возможности

- Локальные аккаунты, отдельная библиотека и MCP-токены каждого пользователя.
- Загрузка аудио/видео, YouTube-ссылки и импорт каждого ролика целого плейлиста.
- Постоянные items: собственные названия, теги и связи сохраняются при недоступности
  внешнего источника. Скачивание добавляет локальный источник к тому же item.
- Предустановленные и пользовательские теги, массовые изменения.
- Ручные и динамические плейлисты: объединение, пересечение, исключение, вложенные
  плейлисты, теги, фильтры, ручные добавления и порядок. Предпросмотр объясняет состав.
- Постоянный ПК-плеер: audio/video/YouTube, очередь, seek, громкость, shuffle,
  повтор и восстановление состояния. Локальный готовый файл приоритетен.
- Долговечные фоновые задания: прогресс, отмена, повтор и восстановление worker.
- Полный или ссылочный ZIP-экспорт, preview импорта и перенос в другой аккаунт
  или установку с переназначением ID, файлами, тегами, плейлистами и настройками.

Сайт и MCP используют одни доменные сервисы. Схемы правил — данные;
произвольный код и SQL из пользовательских настроек не исполняются.

## Установка и запуск

Нужен Node.js >=22.16 и npm. Зависимости закреплены в lockfile.

```bash
npm ci
cp .env.example .env
npm run db:deploy
npm run account -- listener
npm run build
npm start
```

Сайт: [localhost:8790](http://localhost:8790). Сервер отдаёт сайт, API, MCP
и авторизованные файлы; отдельный worker выполняет задания. Аккаунт также можно
создать в интерфейсе. CLI сохраняет пароль в `storage/accounts/listener.json`
с правами 0600, не печатает его и не меняет существующий аккаунт.

Разработка: `npm run dev` — сервер 8790, Vite 5174 и worker. Перед запуском
проверь порты, не запускай второй экземпляр поверх работающего.
Данные остаются в `storage/`, конфигурация — в `.env`; оба исключены из git.
Миграции применяются wrapper-скриптом, который учитывает первый запуск SQLite
на macOS. Останавливай сервер/worker перед изменением схемы работающей БД.

## YouTube и локальные файлы

Для YouTube установи актуальный официальный [yt-dlp](https://github.com/yt-dlp/yt-dlp)
и укажи `YTDLP_PATH` либо добавь бинарник в PATH. Используется Node.js как JS runtime;
для полного YouTube нужна сборка с EJS. FFmpeg поставляется зависимостью приложения.
При необходимости задаётся `YTDLP_PROXY`; системные настройки сети Hibiki не меняет.

Проверка инструментов:

```bash
npx tsx --env-file-if-exists=.env apps/worker/src/main.ts --diagnostics
```

Добавление ссылки не скачивает файл автоматически. Для ролика есть отдельная
команда скачивания audio/video. Поддерживаются публичные и доступные по ссылке
материалы; приватная OAuth-библиотека не входит в MVP. При ограничении получения
форматов одиночная ссылка может получить достоверное название через официальный
YouTube oEmbed; это не гарантия разрешённого встраивания или скачивания.

Для локального импорта агентом разреши папки в `LOCAL_MEDIA_DIRS` (на macOS
разделяются `:`). Исходные файлы копируются, не перемещаются. Обычная загрузка
через сайт не требует доступа к папкам сервера. Несовместимое медиа получает
браузерную MP4/M4A-копию, оригинал сохраняется.

Сейчас media upload ограничен 2 ГиБ на файл, загрузка архива библиотеки — 20 ГиБ,
внутренний медиафайл архива/YouTube download — 4 ГиБ. Результат проверки
архива показывает отсутствующие файлы и совпадения до применения.

YouTube-плеер видим и зависит от политики и доступности YouTube; скрытый iframe
не используется для фонового звука. Ограничения API на скачивание/офлайн-копии,
фоновое воспроизведение и хранение API-данных не отменяются использованием yt-dlp.
См. [правила YouTube](https://developers.google.com/youtube/terms/developer-policies).
Локальные audio/video используют обычный browser media. Телефон и работа
при сне компьютера не входят в первую итерацию.

## Плейлисты

Пример состава: «Опенинги ∪ Эндинги ∪ любимый тег ∪ ручные items − исключения».
Вложенные подборки обновляются по текущим данным. Один item не дублируется,
исключения имеют приоритет, циклы запрещены. Порядок отделён от состава.
Запущенная очередь — снимок: изменения правил не переставляют играющий трек.

В интерфейсе доступен редактор правил и расширенный JSON-режим. Схема версии1
и примеры доступны агенту через `capabilities`; перед сохранением используйте
`playlist_validate` и `playlist_preview`, для разбора — `playlist_explain`.

## Подключение агента

Создай личный токен в настройках сайта. MCP Streamable HTTP:
`http://localhost:8790/mcp`, заголовок `Authorization: Bearer <токен>`.
В `.mcp.json` используется переменная `HIBIKI_MCP_TOKEN`. Не коммить значение.
У каждого вызова заново проверяется владелец; отозванный токен больше не работает.

Основные группы: capabilities; media_list/get/import/upload/update/download;
tags; playlist validate/preview/explain/save; jobs; library export/import.
Долгая операция возвращает jobId; прогресс получай через job_get.
Передача файлов — multipart по одноразовой ссылке, без base64 в контексте агента.

## Проверки и разработка

```bash
npm test
npm run build
npx tsc --noEmit
```

Затем живые проверки затронутых поверхностей: браузер, настоящий MCP,
декодирование/seek медиа, задания и полный перенос. Vitest использует временные
БД и не наследует пользовательский DATABASE_URL. CI запускает ту же тройку.
Проверочные аккаунты, ссылки, медиа и снимки находятся только в storage.

`seed-demo.mjs` и `verify-live.mjs` — воспроизводимые сценарии локального наполнения
и сквозной проверки. Они требуют подготовленный аккаунт/токен в
`storage/verification/01-mvp/access.json`; секреты не входят в репозиторий.
