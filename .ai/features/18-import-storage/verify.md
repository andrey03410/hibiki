# Проверка хранилища и очистки

На итоговом коде `eda74c4` последовательно прошли `npm test` (530 тестов, 55 файлов), `npm run build` и `npx tsc --noEmit`. Отдельный ревьюер проверил весь дифф и подтвердил исправления учёта при переносе, восстановлении после сбоя и обработке старых резервов.

## Сквозная проверка

На изолированной SQLite запущены HTTP-сервер, отдельный процесс worker, Chrome и официальный клиент MCP по Streamable HTTP. Два тестовых аккаунта получили конечные лимиты через локальный HTTP-ответ, совместимый с Kaname. Исходный аккаунт загрузил WAV и экспортировал ZIP. Второй получил одноразовый адрес загрузки через MCP, загрузил ZIP, дождался предпросмотра и применил его.

- Два одновременных вызова применения вернули один ID. ZIP исчез с диска, временный резерв стал нулевым. У получателя остались 16 044 байта WAV. Содержимое проверили побайтовым сравнением, воспроизведение по HTTP Range вернуло 206 с правильным содержимым.
- Подготовили старые успешно применённые архивы в формате предыдущей версии. Очистка из Chrome и через MCP показала фактическую разницу на диске. Отмена в диалоге сохранила ZIP. Архив другого аккаунта и готовый экспорт сохранились. После очистки раздел «Задания» открывал сохранённый результат.
- Загрузка одиночного WAV прошла при лимите в точности 16 044 байта. Для нового импорта ZIP и распакованный WAV одновременно укладывались ровно в выделенную квоту.
- Лимит уменьшили до суммы размеров WAV и одного ZIP. Из двух одновременных загрузок одна прошла, вторая получила HTTP 413. Размер медиа и оставшегося ZIP на диске совпал с суммой квоты.
- Прервали процесс записи после создания временного файла в 32 768 байт. Пока процесс жил, второй процесс получил отказ в резервировании ещё одного байта. После остановки система удалила временный файл и снова разрешила занять 32 768 байт.
- В браузере с заданными ответами API также проверены частичный сбой, повтор, смена аккаунта во время запроса и экран локального аккаунта без квоты.
- На тестовую БД предыдущей версии с двумя записями истории применили миграции дважды. Обе записи сохранились, каждая новая миграция зарегистрирована один раз.

## Что посмотреть на сайте и в MCP

В настройках открыть «Хранилище». Сверить медиа, экспортные и входные архивы, временные резервы и доступный объём. При наличии старых применённых ZIP можно открыть диалог и проверить оценку до подтверждения. В истории соответствующий предпросмотр после очистки открывает прежний результат.

В MCP вызвать `storage_usage`. В `cleanable` находятся количество и суммарный размер подходящих архивов владельца токена. Для очистки вызвать `storage_cleanup` с `{"confirm":true}`. Повторный вызов показывает нулевой результат, если новых подходящих файлов нет.

Перед выкладкой на действующей установке сверили строки учёта и размеры медиа и ZIP на диске для всех шести аккаунтов. Пропавших файлов, расхождений размера, неучтённых ZIP и активных временных резервов в выборке не обнаружено. Проверка была в режиме чтения.

Материалы локальной проверки хранятся в `storage/verification/18-import-storage/` вне Git.
