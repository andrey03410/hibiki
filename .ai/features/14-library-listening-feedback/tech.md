# Технические решения для обсуждения

Предложения относятся к сайту Hibiki. Состояние сверено с кодом на `184e823`. Поиск измерен на отдельной тестовой БД. Для описанного владельцем эпизода с полосой и медленного старта пока нет записи сетевых запросов и событий плеера.

### T01. Сортировка по популярности

Сервер уже обновляет строку `ListeningSummary` на трек. Поле `completed` считает завершённые прослушивания по действующему правилу аналитики. Для записи с известной длительностью это естественное завершение с покрытием минимум 80%. Рекомендация — присоединять сводку по владельцу и ID записи, упорядочивать по `COALESCE(s.completed, 0) DESC, s.lastStartedAt DESC NULLS LAST, i.id ASC`, где i — запись медиатеки, s — её сводка. Предыдущие прослушивания уже учтены. Отдельная загрузка статистики для каждой карточки и пересчёт журнала здесь избыточны. [Запись истории](../../../apps/server/src/history.ts) · [Схема данных](../../../apps/server/prisma/schema.prisma)

### T02. Недавние и согласованный порядок

Использовать `lastStartedAt IS NOT NULL` и убывание `lastStartedAt` со стабильным вторым ключом ID. Учитываются старты реального воспроизведения, включая частичное. Сначала применить все ограничения выдачи, затем порядок и пагинацию. Количество результатов, счётчики тегов, страницы и очередь должны видеть одно ограничение «прослушано». Выборочная чистка детального журнала сохраняет сводки, отключение записи замораживает пополнение, полный сброс очищает и персональную выдачу.

Для двух персональных режимов фиксировать упорядоченные ID при открытии выдачи. Передавать ключ снимка в курсоре последующих страниц и запросе `/api/library/ids`. Тогда запуск первого трека не передвинет записи во время прокрутки. Новый поиск или обновление получает свежие сводки. При удалении записи, полном сбросе или истечении снимка обновить выдачу с первой страницы. Изменение доступности проверять при запуске. Использовать ограниченный по размеру и времени серверный кеш с привязкой к владельцу, параметрам и ревизии. Персональные параметры вынести в браузерную схему, поскольку MCP `media_list` сейчас наследует общую схему фильтров. [Страницы выдачи](../../../apps/server/src/library-pages.ts) · [Клиент медиатеки](../../../apps/web/src/main.tsx) · [История и очистка](../../map/history.md) · [MCP](../../../apps/server/src/mcp.ts)

### T03. Одна перестановка на всю выдачу

Взять упорядоченный по ID набор совпадений, применить существующий Fisher–Yates с фиксированным seed один раз. Через тот же снимок выдавать страницы по 100 и ID для очереди. Вкладка хранит seed вместе с фильтрами аккаунта. «Перемешать ещё раз» создаёт новый seed. Случайная SQL-сортировка на каждую страницу может давать повторы и пропуски. Проверить на 203 записях, что конкатенация трёх страниц равна массиву для «Играть выдачу», а запуск с карточки не ждёт, когда загрузятся остальные ID. [Готовая перестановка](../../../packages/core/src/queue.ts) · [Состояние поиска](../../../apps/web/src/LibrarySearchControls.tsx)

### T04. Полоса воспроизводимого буфера

Сегодня `updateNativeRanges` снимает все интервалы `HTMLMediaElement.buffered`, а общий `PlaybackSeekBar` рисует каждый из них. Отдельный сегмент после перемотки допустим. Конкретный случай владельца требует воспроизведения. Для выбранного UX брать интервал, содержащий реальную позицию движка, рисовать до его конца, при попадании в разрыв скрывать заливку буфера. Мелкую погрешность округления ограничить визуально одним пикселем. Обновлять снимок на progress, seeked, смене длительности/источника и возврате вкладки. Использовать одинаковую модель в обеих панелях. YouTube предоставляет долю загрузки без координат интервалов, поэтому для него достаточно существующего статуса буферизации. [События плеера](../../../apps/web/src/player.tsx) · [Шкала](../../../apps/web/src/PlaybackControls.tsx) · [YouTube IFrame API](https://developers.google.com/youtube/iframe_api_reference#Playback_status)

Проверка — локальный файл на ограниченной сети, перемотка через незагруженный участок, возврат назад и смена источника. Сопоставить время, реальные диапазоны и обе шкалы. Успех — нет заливки через реальный разрыв и сегмента от предыдущего трека.

### T05. Догрузка текущего файла

Маршруты файлов уже поддерживают HTTP Range и возвращают длину. Нативный audio сейчас получает URL напрямую. Начать с замера естественной загрузки и явного `preload="auto"`. Браузер вправе приостановить её. Для режима догрузки до конца рекомендую единый источник байтов для декодера и фонового чтения. На первом запросе он сразу отдаёт начало, дальше учитывает уже принятые диапазоны, последовательно добирает пробелы и при перемотке обслуживает нужный диапазон первым. Проверять полноту по покрытию от байта 0 до размера файла. Фоновый fetch, результатом которого плеер не пользуется, удваивает сетевую работу. [Выдача файлов](../../../apps/server/src/app.ts) · [Заимствованные источники](../../../apps/server/src/sharing-routes.ts) · [HTML Standard, preload](https://html.spec.whatwg.org/multipage/media.html#attr-media-preload)

Кандидат для собственных файлов — посредник в браузере, способный обслуживать Range из временного хранилища блоков и передавать данные до завершения загрузки. До выбора механизма проверить потоковую передачу, перемотку и память в поддерживаемых браузерах на MP3 и M4A, включая контейнер с метаданными в конце. Задать предел временного хранилища. Для больших файлов сверх бюджета сохранять потоковое воспроизведение. Для ответов `private, no-store` (включая Kaname и общие ссылки) использовать только допустимый временный буфер текущего воспроизведения. При новом запуске по ссылке повторять проверку доступа. При отмене запроса, смене владельца или источника освобождать блоки. Для внешнего IFrame работает штатный буфер провайдера.

### T06. Начало следующей записи

Переиспользовать правила выбора кандидата из очереди, включая режим звука, shuffle, repeat и недоступные источники. Предпросмотр кандидата должен быть без побочных эффектов для навигации. Для одного пригодного файла запросить начало с лимитом в байтах. Предлагаю ориентир в пять секунд и потолок 512 КиБ, размер запроса подбирать по формату. Проверить, что из префикса действительно декодируется начало. Использовать тот же механизм чтения, что в T05, с передачей готовых блоков плееру. При повторе текущего, `waiting`, смене порядка или источника убирать ненужный запрос. Проверять доступ к общему файлу при фактическом старте. Для внешнего YouTube не открывать второй плеер. [Переход по очереди](../../../apps/web/src/player.tsx) · [Поиск доступной записи](../../../apps/web/src/queue-catalog.ts)

Приёмка — одна следующая запись, ограничение байтов видно в сети, готовые байты используются при старте, при ожидании текущего трека фоновая загрузка уступает ему сеть, в истории появляется только фактическое воспроизведение.

### T07. Где оптимизировать в первую очередь

В текстовом пути `matchingKeys` перебирает кандидатов пачками по 256, собирает названия, заметки, теги с предками и псевдонимами. На первой странице без выбранных тегов совпадения могут вычисляться дважды — для списка и для счётчиков. С выбранными тегами области действительно различаются, поскольку панель считает доступные теги до наложения текущего выбора. Поле ввода обновляет фильтр при каждом символе. Клиент отбрасывает устаревший ответ, но запрос уже отправлен. [Запросы и кеши](../../../apps/server/src/library-pages.ts) · [Поле поиска](../../../apps/web/src/LibrarySearchControls.tsx) · [Загрузка страницы](../../../apps/web/src/library-pages.ts)

Локальный замер существующего `POST /api/library/page` через Fastify inject на временной SQLite. 4 096 аудиозаписей, 64 дочерних тега, восемь родительских, один дочерний тег на запись. Оба запроса находили одинаковые 512 записей и возвращали первые 100. По пять пар запросов с чередованием сценариев. Для каждой пары создан новый экземпляр приложения с пустыми кешами выдачи и счётчиков. ОС и SQLite могли использовать ранее прочитанные страницы. Замер включает сервер и сериализацию.

| Выборка | Первый запрос, медиана (разброс) | Повтор, медиана |
|---|---:|---:|
| Родительский тег кнопкой | 13 мс (10–68) | 9 мс |
| Название того же родителя в строке поиска | 45 мс (40–67) | 9 мс |

Сначала объединить одинаковые проходы для списка и счётчиков. Добавить короткую задержку отправки именно при вводе текста (предложение — 150 мс), отменять устаревшее чтение и проверять отмену между SQL-пачками. Клик по тегу и очистку строки выполнять сразу. Затем измерить выбранные теги с И/ИЛИ, наследование, псевдонимы, кириллические подстроки и большие выборки. До решения об индексе проверить планы SQLite и стоимость обновления связей. Новый поисковый индекс оправдан, если этих изменений недостаточно и совпадения по подстрокам и личным заметкам сохраняются. [SQLite EXPLAIN QUERY PLAN](https://www.sqlite.org/eqp.html)

Для аудио снять временную последовательность «клик → обращение за источником → первый байт → playing», задержку между ended и следующим playing, число остановок, повторно скачанные байты и пик памяти. Сравнить локальную запись, запись по ссылке и YouTube, холодный и тёплый старт, обычную и ограниченную сеть. Измерять p50/p95 на повторяемой серии до и после каждого изменения. Свой файл с уже загруженной карточкой должен начинать играть независимо от подсчёта тегов и получения всех ID очереди. Приоритет следующего трека проверить сравнением с отключённой предзагрузкой.
