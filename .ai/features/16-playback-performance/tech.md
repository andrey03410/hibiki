# Технические решения для обсуждения

Сверено с кодом на `b148eb0` и с продом 25 ноября 2026. Все решения — предложения.
Сводка проблем и целевые показатели — в [product.md](product.md), сырые замеры —
в `storage/verification/16-playback-performance/` вне Git.

## Исходная система

### Доставка звука

- Собственный файл ≤ 32 МиБ в звуковом режиме идёт через ретранслятор:
  [audio-worker.js](../../../apps/web/public/audio-worker.js) перехватывает
  `/files/:id?hibiki-audio=…` и передаёт запрос во вкладку.
  [audio-delivery.ts](../../../apps/web/src/audio-delivery.ts) держит байты в памяти,
  каждый кусок 64 КБ — один обмен сообщениями с вкладкой.
- Лимит `MAX_FILE = 32 MiB` и блок `BLOCK = 1 MiB` (audio-delivery.ts:3–5).
  Догрузка `fill()` запрашивает блоки строго по одному, с приоритетом `low`
  (audio-delivery.ts:81–126, 154–162). Между блоками простаивает один RTT.
- Префикс `ownedAudioFile` = min(512 КиБ, 5 с × средний битрейт) (audio-delivery.ts:9–18).
  Заголовок файла не учитывается. Хвост M4A заранее берётся только для следующего
  трека (`prepareMetadata`, :145–152).
- Подготовка следующего включается при `canPrepareNext`: идёт воспроизведение
  и есть запас 5 с (player.tsx:430–460). Завершение загрузки текущего не учитывается.
- `select()` при повторном использовании подготовленного файла сначала ждёт
  HEAD-запрос `authorize()` (audio-delivery.ts:185–189, 237–248, 266).
- Файл > 32 МиБ, общий или без поддержки ретранслятора играет через
  `<audio src=/files/:id preload=auto>` (player.tsx:1903). Chrome держит буфер
  примерно на 25 с вперёд и полностью файл не загружает.
- Шкала строится по `HTMLMediaElement.buffered` (player.tsx:886–900). Байты в памяти
  вкладки она не видит.

### Звуковой режим и видео

- `playbackSources(item, "audio")` выбирает локальные источники с `hasAudio`.
  Видео с дорожкой звука подходит, если нет аудиофайла (player-model.ts:142–165).
- Скачивание с YouTube: режим звука — `bestaudio[ext=m4a]` с извлечением,
  режим видео — `bestvideo[≤1080, avc1]+bestaudio[mp4a]` в MP4 (youtube.ts:471–480).
  Отдельной звуковой копии у видео нет.
- В `media.ts` уже есть перепаковка через FFmpeg с `-map` и `-c:a copy`
  и `+faststart` (media.ts:219–240). Это основа для копии без перекодирования.

### Фон и данные интерфейса

- `/api/library/overview?playlists=summary` каждые 3 с независимо от изменений
  и видимости вкладки (main.tsx:437–469). Ответ 236 КБ: 1 015 тегов (162 КБ),
  счётчики (42 КБ), задания, плейлисты. Изменение определяется `JSON.stringify`.
- `api()` возвращает `undefined` при успешном статусе и неразбираемом теле
  (api.ts:39–43). `setOverview(undefined)` роняет `App` без error boundary.
- Плеер: `PUT /api/settings` каждые 5 с (player.tsx:1357). `cachePlayback`
  записывает всё состояние вместе с очередью в localStorage на каждый `timeupdate`
  (player.tsx:1304, замер — 3,9 записи/с). Контрольная точка истории — 15 с
  (listening-client.ts:60). Общие плейлисты опрашиваются каждые 5 с
  (use-sharing-request.ts:4), уведомления YouTube — каждые 30 с.
- Каждый `/api` и `/files` запрос в режиме Kaname: сессия, строка пользователя,
  HTTP-запрос в Kaname (~4 мс) и для `/files` upsert активности (app.ts:127–171).
  Сборка полного каталога не блокирует отдачу файлов (HEAD 3–14 мс во время неё).

### Плейлисты и обложки

- Форма создания и редактор правил загружают `GET /api/library` — полный снимок
  `library.snapshot` (app.ts:206–209): 5,1 МБ, 3,0 с на сервере.
- После создания `detail?limit=24` запрашивается дважды.
- Обложки: `ArtworkService` хранит в памяти 8 оригиналов, 512 миниатюр и 32 крупные
  (artwork.ts:176–181). Каждая миниатюра — запуск FFmpeg, параллельно 2.
  Ответ `private, no-cache` (app.ts:243–256): при перепроверке без кеша сервер
  снова вычисляет миниатюру ради ETag.

### Доставка сайта

- Caddy проксирует `:8443` без `encode` — ответы не сжимаются.
- `@fastify/static` отдаёт `/assets/*` с хешем в имени как `public, max-age=0`
  (app.ts:559).

## Решения

### T01. Звуковая копия видеозаписи без перекодирования

- Варианты: (а) копия при скачивании с YouTube; (б) фоновое задание worker
  для каждой видеозаписи с `hasAudio` без звукового источника, плюс новые
  загрузки; (в) перепаковка на лету при каждом запросе; (г) разбор MP4
  в браузере через MSE.
- Рекомендация: (б), можно вместе с (а) для новых скачиваний. Команда FFmpeg
  `-map 0:a:0 -c:a copy -vn -sn -dn -map_metadata 0 -movflags +faststart` → `.m4a`
  для AAC. Для Opus в WebM — `.webm` или `.ogg` тем же копированием.
  Результат — новый `MediaFile` kind=audio и `Source` того же item с признаком
  производной копии (`derivedFromFileId`). Пакеты звука проверяются побайтно,
  хеш дорожки в оригинале и копии сравнивается через `-f streamhash`.
  `playbackSources` в звуковом режиме уже сортирует kind=audio первым,
  поэтому меняются только данные. Перенос: копия не экспортируется и
  пересоздаётся. Удаление оригинала удаляет копию. Квота — по решению P03.
  Вариант (в) ломает Range и перемотку. (г) сложен, плохо работает в Safari
  и всё равно качает видео.
- Объём: 346 видеофайлов, 15,1 ч. Звук 128–386 кбит/с, итого ~1–2,6 ГБ.
  Перед запуском проверить свободное место (сейчас 5,7 ГБ) и ограничить задание
  порогом свободного диска.
- **Решение:** ждёт владельца.

### T02. Полная загрузка текущего трека без простоев

- Варианты: (а) оставить блоки по 1 МиБ; (б) после префикса один потоковый
  запрос `Range: bytes=N-` до конца файла, разрыв только при перемотке
  в незагруженное место; (в) запускать 2–3 блока параллельно.
- Рекомендация: (б). Простоя между блоками нет, один TLS-поток на HTTP/2.
  После `playing` приоритет `auto`, пока текущий не загружен. Таймаут простоя
  потока 10 с, затем повтор с места остановки. Сейчас зависший блок держит
  «Буферизацию» до 30 с. Лимит `MAX_FILE` поднять до 128 МиБ: с копиями из T01
  больше 54 МБ звука на прод нет. Для видео в видеорежиме — нативный поток.
- **Решение:** ждёт владельца.

### T03. Префикс по реальному заголовку файла

- Варианты: (а) разбирать заголовок в браузере после первого блока;
  (б) сохранить подсказки на сервере при импорте и проверке файла:
  `audioStart` (конец ID3v2 или `moov` перед `mdat`), `tailStart` для M4A
  с индексом в конце, средний битрейт. Отдавать их в `SourceDto`.
- Рекомендация: (б) с запасным (а). Префикс = `audioStart` + 10 с звука, потолок 2 МиБ.
  Для `tailStart` хвост загружается сразу вместе с началом и для текущего трека.
  Заполнение для 2 970 существующих файлов читает только заголовки: секунды
  работы worker. Это убирает 1,85-секундный старт у 212 MP3 и 93 M4A.
- **Решение:** ждёт владельца.

### T04. Порядок «текущий целиком → начало следующего»

- Рекомендация: заменить `reserve` в `canPrepareNext` на признак
  «текущий `AudioBytes` загружен полностью». Подготовка следующего — только
  после этого, с приоритетом `low`, одна запись, размер по T03. При
  перемотке текущего в незагруженное место подготовка следующего ставится
  на паузу. Отмена при смене очереди — как сейчас.
- **Решение:** ждёт владельца.

### T05. Переход без HEAD-запроса

- Рекомендация (по P06): для своих файлов использовать подготовленные байты
  сразу. Доступ подтверждается первым запросом догрузки: 401, 403 или 404
  останавливают воспроизведение и очищают буфер. Для общих источников HEAD
  отправляется параллельно со стартом. Ожидаемый выигрыш — один RTT
  на каждом переходе.
- **Решение:** ждёт владельца.

### T06. Шкала по загруженным байтам

- Рекомендация: `AudioDelivery` публикует покрытие байтов. Полностью загруженный
  файл = вся шкала. Частичную загрузку показывать объединением `buffered`
  и непрерывного участка байтов от текущей позиции, переведённого во время по
  `(байт − audioStart) / (size − audioStart) × duration`. Для VBR это
  оценка, поэтому шкала не заходит дальше фактической границы загруженных байтов.
  Правило P04 из задачи 14 сохраняется: далёкие островки не закрашиваются.
- **Решение:** ждёт владельца.

### T07. Фоновый опрос только изменений

- Варианты: (а) ETag и 304 на `overview`; (б) `GET /api/library/overview?since=<revision>`
  возвращает 204 при неизменной ревизии, иначе полную сводку; (в) SSE-поток событий.
- Рекомендация: (б). Ревизия уже есть в DTO. При неизменных данных сервер
  не собирает сводку. Опрос каждые 10 с только при видимой вкладке, сразу
  при `visibilitychange` и `focus`. Задания — отдельным лёгким запросом
  раз в 3 с, пока есть queued/running. Общие плейлисты на `/playlists` —
  тот же приём. Проверить частые `GET /api/history/preference`: в браузере
  их было до одного в 2 с, вероятно из-за событий видимости.
  Вариант (в) лучше по задержке, но держит соединения через Caddy и сложнее.
  При нагрузке Hibiki он не нужен.
- **Решение:** ждёт владельца.

### T08. Сохранение состояния плеера

- Рекомендация: очередь записывать в localStorage только при её изменении,
  позицию — не чаще раза в 5 с, при паузе и `pagehide`. `PUT /api/settings`
  отправлять без очереди, если она не менялась. Это лёгкий PATCH позиции
  или текущая схема с признаком. Сейчас запись мала (очередь 59 ID, 4,9 КБ),
  но «Играть выдачу» на 2 668 ID даст ~100 КБ × 4 раза в секунду.
- **Решение:** ждёт владельца.

### T09. Сжатие и кеш ответов сайта

- Рекомендация: в Caddy для `:8443` включить `encode zstd gzip` с исключением
  `/files/*` и обложек (`/api/items/*/artwork`). Медиа не сжимается и не меняется,
  Range сохраняется. `/assets/*` отдавать с `public, max-age=31536000, immutable`,
  `index.html` и `audio-worker.js` — с `no-cache`. Ожидаемо: overview
  236 → ~25 КБ, страница выдачи ~200 → ~20 КБ, JS 476 → ~140 КБ.
  Caddyfile живёт на VPS вне репозитория. Изменение выкладывается через
  `release.sh`/ручную правку с проверкой, способ закрепить в deploy-скилле.
- **Решение:** ждёт владельца.

### T10. Редактор плейлиста без полного каталога

- Рекомендация: убрать `GET /api/library` из формы. Выбор записей уже умеет
  страницы по 100 через поиск. Правила по тегам берут теги из сводки.
  Для подсказок по записям использовать `POST /api/library/page`, для
  проверки правил — существующий `preview`. Убрать повторный `detail`
  после создания. Если где-то нужен полный набор ID — `/api/library/ids`.
- **Решение:** ждёт владельца.

### T11. Устойчивость к обрыву ответа

- Рекомендация: `api()` выбрасывает ошибку, если тело ожидалось и не разобрано.
  Обновление сводки игнорирует некорректный ответ. Error boundary вокруг маршрутов
  и плеера: при сбое — сообщение и «Повторить», плеер продолжает играть.
  Регрессионный тест: успешный статус и обрезанный JSON.
- **Решение:** ждёт владельца.

### T12. Обложки на диске

- Рекомендация: миниатюры и cover-WebP сохранять в `storage/cache/artwork/<fileHash>-<size>.webp`.
  Ключ — hash файла, поэтому кеш переживает деплой. Отсутствие обложки
  тоже кешировать (маркер). Адрес обложки включает hash, ответ
  `private, max-age=31536000, immutable`: браузер не перепроверяет.
  Права на запись проверяются как сейчас. Оригиналы не меняются.
  Очистка — при удалении файла. Объём ~5–30 КБ на запись, ~100 МБ на всю медиатеку.
- **Решение:** ждёт владельца.

### T13. Повторяемый замер

- Рекомендация: закрепить сценарий этого аудита скриптом Playwright с перехватом
  записи истории и очереди. Метрики: клик→playing, ended→playing, байты на трек,
  фоновые байты в минуту, открытие редактора, время ввода в поиск → карточки.
  Прогон на проде до и после каждого этапа плюс серверный замер на копии БД.
  Без этого прироста не доказать.
- **Решение:** ждёт владельца.

## Порядок внедрения (предложение)

1. Быстрые и безопасные: T09, T07, T08, T11, T04, T05. Это жалоба 3 и фоновый трафик.
2. Звук: T03, T02, T06. Быстрый старт, полная загрузка, честная шкала.
3. Видео в звуковом режиме: T01 с заданием и проверкой диска. Жалоба 2.
4. Плейлисты и обложки: T10, T12.

Каждый этап — отдельные коммиты в этой ветке с замером T13 до и после.

## Риски

- Диск прода занят на 90%. T01 добавляет до 2,6 ГБ, T12 — ~100 МБ. Нужен порог
  и сообщение в заданиях.
- Память вкладки: полный трек до 128 МиБ плюс до 2 МиБ следующего. С T01
  реальные размеры звука на проде ≤ 54 МБ.
- Safari и сервис-воркер: при отсутствии поддержки остаётся нативный поток.
  Для звуковых копий из T01 он тоже не качает видео.
- Изменение Caddy затрагивает и соседние сайты на этом же Caddy. Правка только
  в блоке `:8443`.
