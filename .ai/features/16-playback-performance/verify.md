## Проверки реализации

- Перед работами сверены содержимое 2 970 файлов с SHA-256 и контрольные суммы
  карточек, правил плейлистов, связей тегов, настроек и истории.
- Живой клиент MCP в изолированной установке получил импортированную карточку.
  Второй аккаунт прочитал Range общей виртуальной дорожки до отзыва ссылки.
  При повторном обращении после отзыва сервер вернул 404.
- При полном ZIP-переносе в другой аккаунт совпали хеш оригинала, хеш виртуальной
  дорожки и порядок записей в плейлисте. В архив вошёл один исходный медиафайл.
- В локальных Chrome и WebKit проверены декодирование, перемотка, офлайн-буфер,
  граница предзагрузки, прокрутка очереди из 2 668 записей, обрыв JSON во время
  воспроизведения и редактирование плейлиста.
- В пробной загрузке YouTube звуковые пакеты исходного WebM, полученного Ogg
  и дорожки видеоверсии MP4 дали одинаковый SHA-256.

## MCP

Клиент SDK выполнил 58 исходных измерений с личным токеном. В серии из
10 чтений медианы составили 52 мс для карточки, 136 мс для списка из 50 записей,
301 мс для текстового поиска и 255 мс для плейлиста. Ошибок в серии не было.
Токен отозван, список прежних токенов проверен. Для `/api/me` при попеременных
20 запросах с каждым типом авторизации медианы cookie и Bearer составили 43 мс.

В изолированной установке настоящий MCP-клиент проверил замену короткого
источника полным, оба режима воспроизведения, идемпотентность, отмену и повтор.
Проверены два владельца, права на источники и сохранение полей и связей карточки.

Проверены все 2 975 файлов, которые были в аккаунте к концу первой выкладки.

Первое приложение раскатывалось целиком после отдельного изменения Caddy.

Первые 100 запусков выявили задержки при чтении ID3 и переключении во время
догрузки. Вторая итерация проверяет именно эти случаи.


В дополнительной проверке React Profiler одни и те же 100 карточек с шестью
тегами открывались в двух production profiling-сборках на локальном стенде.

снизилась с 8,6 до 0,1 мс, p95 с 10,2 до 0,3 мс. Это время работы React,
пользовательская задержка до звука измерена отдельным браузерным сценарием.


Для ускорения построения представления проведён A/B в четырёх отдельных
процессах на том же VPS, в порядке A/B/B/A, по 24 построения. На MP4 размером
214,9 МБ p50 / p95 уменьшились с 12,26 / 46,49 до 6,36 / 28,71 мс. Максимум
из 48 построений новой версии составил 30,00 мс, последовательное чтение
дало 58,66–68,25 МБ/с. Полные SHA-256 старого и нового виртуальных файлов
совпали во всех четырёх процессах.


## Стабильность MCP при выкладке

За десять минут с одним токеном выполнены 41 чтение и пять подключений SDK.
Одно чтение получило 502. В это время независимо выкатывался PR №21. Caddy
записал отказ TCP-соединения с Hibiki в 10:14:18 UTC, контейнер запустился
в 10:14:15 UTC. Следующий запрос с тем же токеном прошёл, временный токен
отозван по окончании серии. В следующей десятиминутной серии прошли все 41 чтение
и пять подключений. Для всех 46 операций медиана составила 142 мс, p95 — 211 мс.
Единственное чтение дольше секунды (1 574 мс) началось около 10:39:02 UTC. В тот момент новый контейнер следующего релиза №23 проверял миграции перед запуском. Клиент получил нормальный ответ с тем же токеном. После отзыва токена
повторное обращение к MCP вернуло HTTP 401.


## Видеорежим до доработки

В каталоге владельца на момент замера было 280 видеокарточек с рабочим локальным
источником. Исходный MP4 размером 214,9 МБ и длительностью 357,61 с открывали
трижды в каждом движке. После первых 10 секунд перематывали вперёд. Для WebKit
байты получены из событий сетевого инспектора.

| Медиана трёх запусков | Chrome | WebKit |
|---|---:|---:|
| До первого отображённого кадра | 381 мс | 847 мс |
| Видео перед текущей позицией на десятой секунде | 14,57 с | 40,60 с |
| Получено за первые 10 с | 14,65 МБ | 32,46 МБ |
| От перемотки до следующего кадра | 475 мс | 1 620 мс |

Контрольное чтение того же URL единым диапазоном по 12 МиБ дало 3,82–10,13 МБ/с.
Серии запускались последовательно. Звук из видео и показ оригинального видео
измеряются отдельно.


Отдельно настоящий клиент SDK вызвал `media_replace_source` с URL общедоступного
ролика YouTube в изолированной установке. Worker сам скачал и подготовил
видеозапись. Длительность исходного отрывка 1,023 с сменилась на 19,021 с.
ID, пользовательское название, избранное и тег сохранились. Повтор вернул
уже применённую замену. Вторым вызовом с прежним `sourceId` вернули отрывок
на исходную карточку. Производственные карточки для этого сценария не менялись.
