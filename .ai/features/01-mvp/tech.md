# Технические решения

**Статус:** подтверждено владельцем 17 ноября 2026 года. Разрешена полная
реализация автономно до merge. Смешанные плейлисты audio/video обязательны.
Ниже сохранены варианты и рекомендации, принятые этим подтверждением.

## Исходная система

В Hibiki сейчас только документы, git-настройки и скиллы. Кода и зависимостей нет.
Проверены соседние проекты:

- Asobiba: `apps/server/src/mcp/routes.ts` — Fastify и MCP Streamable HTTP с личным
  токеном; доменные сервисы общие для сайта и MCP. `package.json` — npm workspaces;
  сервер использует SQLite/Prisma, сайт — React/Vite, контракты — Zod.
- Douga: `src/lib/ytdlp.ts` — подготовка бинарника, запуск процесса, probe и download;
  `src/lib/domain/ytdlp-args.ts` — выбор формата и разбор прогресса;
  `src/server/downloads.ts` — задания в БД, процессы в памяти, выполнение внутри Next.
  Это пригодные образцы, но не готовая переносимая библиотека Hibiki.
- Потерю активных процессов при рестарте из Douga не переносить: у Hibiki задания
  должны восстанавливаться по сохранённому состоянию.

Ни один файл реализации из соседних проектов в основу Hibiki не скопирован.
Скиллы feature/verify перенесены с адаптацией предметной области и фактического состояния.

## Решения

### T01. Стек

- Варианты: TypeScript/Fastify/React; Next.js; Python/FastAPI с отдельным фронтендом.
- Рекомендация: TypeScript, поддерживаемая Node.js LTS, npm workspaces, React/Vite/
  React Router, Fastify, SQLite/Prisma 7, Zod 4, официальный SDK MCP, Vitest.
- Причина: общие схемы и логика клиента/агента, опыт Asobiba, простой локальный запуск.
  SSR для личной медиатеки не нужен. yt-dlp/FFmpeg работают дочерними процессами.
- Версии зафиксировать при реализации после проверки совместимости; не ставить
  `latest` вслепую. Prisma 7 выбран как знакомая поддерживаемая SQLite-линия.
- **Решение владельца:** подтверждено вместе с техникой 17 ноября 2026 года.

### T02. Архитектура и размещение

- Варианты: единое приложение; несколько сервисов.
- Рекомендация: модульный монолит. Один сервер отдаёт собранный сайт, API, файлы
  и `/mcp`; отдельный worker выполняет долгие задания. БД и storage на локальном диске.
- Предлагаемые, ещё не созданные пути: `apps/web`, `apps/server`, `apps/worker`,
  `packages/contracts`, `packages/core`. Провайдеры и хранилище — адаптеры сервера,
  ядро не зависит от HTTP/MCP/React. Не дробить пакеты без нужды.
- Пользовательские медиа и проверочные данные — только `storage/`, вне git.
  Базовое размещение: сервер 8790, Vite 5174; проверить доступность портов перед
  фиксацией и запуском. Asobiba/Douga должны продолжать работать независимо.
- **Решение:** предложено агентом; порты пока не назначены работающему приложению.

### T03. Данные и идентичность

- Основные сущности: User, MediaItem, MediaSource, MediaFile, Tag, ItemTag,
  Playlist, Job и пользовательские настройки/состояние плеера.
- У MediaItem постоянный ID и ownerId; собственные метаданные отделены от данных
  источника. MediaSource описывает provider/externalId или локальный MediaFile.
  Доступность и время последней проверки относятся к источнику.
- Повтор YouTube-import узнаётся по owner/provider/videoId. Скачивание добавляет
  локальный источник. Файлы распознаются по SHA-256; физическая дедупликация не
  должна объединять разные пользовательские items без явного решения.
- Пути файлов относительны storage; переносимый манифест не содержит абсолютных путей.
- SQLite: foreign keys, WAL, короткие транзакции, согласованное сохранение БД и файлов.
- **Решение владельца:** подтверждено вместе с техникой 17 ноября 2026 года.

### T04. Движок плейлистов

- Варианты: отдельные ручные/умные/составные сущности; единый документ правил.
- Рекомендация: версионированная Zod-схема AST: items, playlistRef, tag/filter,
  union, intersection, difference; отдельное описание порядка.
- Один валидатор и evaluator для API/MCP/UI. Проверять владельца всех ссылок,
  отсутствующие зависимости, циклы, бюджет размера и вложенности документа.
- Вычислять по текущим данным медиатеки; на малой нагрузке кэш не обязателен.
  Результат содержит стабильные ID, порядок и объяснение происхождения/исключения.
- При ссылке на удаляемый плейлист сообщать о зависимостях; не менять молча правила
  зависимых плейлистов. Импорт проверяет весь граф до применения.
- **Решение владельца:** подтверждено вместе с техникой 17 ноября 2026 года.

### T05. YouTube

- Варианты метаданных: официальный Data API; yt-dlp. Воспроизведение: IFrame либо
  готовый локальный файл. Это разные способы с разными ограничениями.
- Рекомендация для личной установки: изолированный адаптер yt-dlp для метаданных,
  состава плейлистов и опционального скачивания; IFrame для доступных ссылок.
  Поддержка публичных и доступных по ссылке материалов, без приватных OAuth-библиотек.
- Извлечение состава не должно скачивать все файлы. Краткий список может содержать
  неполные метаданные: дополнить их отдельно при необходимости, сохранив частичный успех.
- Полная поддержка YouTube в yt-dlp требует EJS и поддерживаемого JS runtime;
  FFmpeg/FFprobe нужны для подготовки и проверки медиа. Предусмотреть диагностируемую
  версию/обновление инструментов и ошибки провайдера, не бесконечные повторы.
- Дочерний процесс запускается массивом аргументов без shell. Принимать только
  поддерживаемые YouTube-адреса, нормализовать их; таймаут и отмена обязательны.
- **Ограничение:** API-политика YouTube ограничивает скачивание/офлайн-копии,
  скрытый фоновый плеер и хранение полученных через API данных. yt-dlp не превращает
  эти сценарии в официально разрешённые возможности API. Собственные метаданные
  отделить от provider cache; не обещать соответствие всей комбинации правилам API.
- **Решение:** предложено агентом; ограничения обсуждены, не выдавать за снятые.

### T06. Задания и файлы

- Варианты: операции в HTTP/MCP-запросе; долговечная очередь.
- Рекомендация: Job в SQLite, отдельный worker, атомарное получение задания,
  lease/heartbeat, bounded retry и отмена. Импорт сохраняет прогресс по позициям.
- После сбоя повторяются незавершённые шаги; идемпотентность не создаёт лишние items.
  Сначала временный файл, затем проверка/переименование и публикация готового источника.
  Ошибки файловой системы не оставляют item с фиктивным готовым файлом.
- Клиент получает jobId, статус и отчёт. UI может опрашивать API; отдельный брокер
  и Redis не нужны. Таймаут вызова агента не уничтожает уже созданное задание.
- **Решение владельца:** подтверждено вместе с техникой 17 ноября 2026 года.

### T07. Сайт и плеер

- React-плеер выше маршрутов; единая очередь и адаптеры local audio/video и YouTube.
  После перезагрузки состояние восстанавливается, а старт со звуком учитывает
  требование пользовательского действия браузера.
- Локальные файлы отдаются потоком с HTTP Range. Оригинал сохраняется; совместимая
  копия готовится, если браузер не поддерживает контейнер/кодек. HLS не нужен для MVP.
- Shuffle — однократная перестановка очереди с сохранённым порядком; предыдущий
  трек возвращает к реально прослушанному item. Состав плейлиста и очередь различаются.
- Для свёрнутого окна использовать обычное продолжающееся воспроизведение local
  media и проверить его на целевом ПК. Не обещать работу во сне/при выгрузке вкладки.
  YouTube проверяется отдельно с учётом API-политики, без скрытого фонового iframe.
- **Решение:** продуктовый приоритет сворачивания задан владельцем; техника предложена.

### T08. MCP и аккаунты

- Варианты: собственный встроенный ИИ; внешний агент через MCP.
- Рекомендация: MCP Streamable HTTP в сервере, личные отзываемые токены; сайт
  использует cookie-сессии. Простые локальные аккаунты, без социальной авторизации.
- Инструменты: capabilities, поиск/импорт/пакетные правки медиа и тегов,
  validate/preview/explain/save плейлистов, jobs, экспорт/импорт.
- Схемы Zod дают runtime-проверку и JSON Schema. Стабильные коды ошибок, пагинация,
  идемпотентные повторы. На каждом вызове заново проверяется пользователь и владение.
  Загрузка файлов — обычный поток по авторизованному upload URL, не base64 в MCP.
- **Решение владельца:** подтверждено вместе с техникой 17 ноября 2026 года.

### T09. Перенос и резервное копирование

- Версионированный переносимый манифест, потоковый архив с поддержкой больших файлов,
  относительные пути и SHA-256. Режимы: метаданные/ссылки либо полная библиотека.
- Предпросмотр импорта проверяет версию, файлы, хэши и граф плейлистов; при применении
  сопоставляет ID и владельца. При конфликте собственных названий не затирать их молча.
  Архив не исполняет код и не может записывать файлы за пределами целевого storage.
- Пользовательский экспорт не включает пароли/сессии/токены; резервная копия всей
  установки — отдельный согласованный снимок БД через SQLite backup и storage.
  Для MVP не обещать резервное копирование работающей установки без согласования файлов.
- **Решение владельца:** подтверждено вместе с техникой 17 ноября 2026 года.

### T10. Реализация и качество

- План только после сигнала владельца. Новое поведение — через содержательные тесты.
- После последних правок: `npm test` → `npm run build` → `npx tsc --noEmit`.
- Затем реальный браузер, настоящий MCP, реальные media decode/seek/download,
  прерывание/восстановление задания и экспорт/импорт под другим аккаунтом.
- Результаты и ограничения — в verify.md задачи, данные и доказательства — в storage.
- **Решение:** предлагается сохранить процесс Asobiba/Douga, как запросил владелец.
