# Технические решения

## Исходная система

Проверено по коду main `301e7f0` и на проде 27 ноября 2026 года.
Зоны: [сайт](../../map/web.md), [медиа](../../map/media.md).

### Звук

Звук загружает вкладка через `AudioDelivery`
([audio-delivery.ts:383](../../../apps/web/src/audio-delivery.ts)). Байты хранятся в памяти
вкладки. Родной `<audio>` получает их через ретранслятор сервис-воркера
([audio-worker.js](../../../apps/web/public/audio-worker.js)). Порядок загрузки после
задачи 16: префикс с индексом, затем один поток до конца. У записи с видео звук отдаётся
виртуальным файлом `/files/:id/audio` без копии на диске. Фоновая догрузка отправляет
серверу желаемую скорость через `x-hibiki-audio-rate`
([media-pacing.ts](../../../apps/server/src/media-pacing.ts)). Срочные запросы не стоят в очереди за ней.

Шаблон сервис-воркера уже принимает `/files/:id` без `/audio` и общие `sources/:id`.
Ретранслятор подходит и для видео без изменения маршрутов.

### Видео

С задачи 19 звук ведёт `<audio>`, а изображение показывает беззвучный `<video>`
([ClipVideo.tsx](../../../apps/web/src/ClipVideo.tsx)). Его часы подстраиваются под звук.

- `<video>` создаётся только на `/player`
  ([player.tsx:359](../../../apps/web/src/player.tsx), `queueMode` в строке 1749).
  В звуковом режиме видео не загружается совсем: ни индекс, ни кадры.
- Своё видео читается родным Range-загрузчиком Chrome. Chrome держит около 20 с вперёд,
  дальше не загружает.
- Общее видео грузит управляемый MSE-загрузчик
  ([video-stream.ts](../../../apps/web/src/video-stream.ts)): окно 48 МиБ, не больше 75 с,
  обрезка позади. В буфер попадают обе дорожки, поэтому звук загружается второй раз.
- `hold(true)` ([ClipVideo.tsx:52](../../../apps/web/src/ClipVideo.tsx)) ставит звук на паузу.
  Это происходит при любой перемотке `leader.seeking`, если через 400 мс после открытия
  нет кадра и при рассинхроне больше 0,35 с. Тогда же `setState("loading")` скрывает
  видео через `visibility: hidden` (строка 166) и показывает «Загружаем видеоряд…».
- Полоса перемотки строится из буфера звука
  ([player.tsx:1709](../../../apps/web/src/player.tsx)). В видеорежиме она показывает
  загруженный до конца звук, а видео загружено на 20 с.

### Замеры

Встроенный браузер, прод, аккаунт andrey. Минимальная задержка сети в этом браузере
около 200 мс. Сырые данные — в `storage/verification/22-video-loading/`.

| Сценарий | Результат |
|---|---|
| Звук записи с видео из медиатеки | Клик → playing за 361–419 мс. Префикс и один поток `bytes=N-`. Префикс следующего — через 4,5 с |
| Unity, 7,9 МБ: «Открыть видео» | `<video>` создан через 35 мс. Метаданные — 684 мс, кадр — 743 мс. Звук на паузе с 439 по 743 мс |
| Unity: перемотка в загруженное | Видео скрыто около 57 мс |
| Unity: перемотка дальше загруженного | Заглушка и тишина 392 мс |
| Gravitation, 163 МБ, 4,5 Мбит/с: «Открыть видео» | Метаданные — 600 мс, переход к позиции — ещё 1063 мс. Заглушка 1,8 с, звук молчит 1,4 с |
| Gravitation: перемотка вперёд в буфер | 19 мс |
| Gravitation: перемотка назад в буфер | 311 мс, декодирование интервала между ключевыми кадрами |
| Gravitation: перемотка дальше буфера | 683 мс |

Видео на проде: 346 файлов, в среднем 2081 кбит/с, самый крупный — 205 МБ.
Интервал между ключевыми кадрами: медиана 3,3 с, p90 — 5,3 с, максимум — 10,25 с.
Индекс `moov`: медиана 121 КБ.

## Причины

1. **Холодный старт видео.** При открытии `/player` у вкладки нет ни индекса, ни кадров.
   Последовательно идут три запроса: заголовок и индекс, байты у позиции,
   данные до ключевого кадра. Каждый занимает 0,2–0,6 с.
2. **Звук ждёт видео.** `hold` превращает задержку картинки в тишину.
3. **Видео скрывается при любой перемотке.** Даже при кадре в буфере на время
   `seeking` выставляется `loading`.
4. **Полоса показывает не то.** Перемотка в «заполненную» часть часто попадает за 20 с
   родного буфера видео.
5. **Нет единого порядка загрузки.** Звук, видео Chrome и MSE-загрузчик качают независимо.
   Ни один из них не знает про режим экрана и следующую запись.

Про звук. Замедление относительно задачи 16 в замерах не подтвердилось. Возможная
причина у владельца — в видеорежиме родной загрузчик видео делит канал со звуком.
Единый планировщик T02 даёт звуку приоритет. T06 добавляет замеры в обычном Chrome.

## Решения

### T01. Чем загружать видео

- Варианты:
  - А. Родной `<video>`, байты отдаёт вкладка через существующий ретранслятор.
    Как у звука: вкладка решает, что и когда качать, а Chrome сам разбирает MP4,
    переходит по ключевым кадрам и декодирует.
  - Б. MSE для всех видео: расширить `video-stream.ts` на своё видео и оставить в буфере
    только видеодорожку.
  - В. Оставить родной Range-загрузчик Chrome и добавить подсказки `preload`.
- Рекомендация: А. Одна схема для своего и общего видео. Нет лимита SourceBuffer
  около 150 МБ, который мешает догрузить видео до конца. Нет повторной загрузки звука
  в MSE. Перемотка внутри загруженного идёт из памяти. В варианте В Chrome не даёт
  управлять окном и приоритетами. MSE-загрузчик после перехода можно удалить.
- **Решение:** принята рекомендация (владелец, 27.11.2026).

### T02. Единый планировщик загрузки

Вкладка держит одну очередь для звука и видео текущей и следующей записи.
Приоритеты сверху вниз:

1. Байты, которые сейчас ждёт декодер звука или видео.
2. Звук текущей записи до конца, как в задаче 16.
3. Индекс видео текущей записи, если у неё есть видео. Около 120 КБ.
4. Окно видео ±10 с у позиции. В звуковом режиме — по намерению P01, в видеорежиме — всегда.
5. В видеорежиме: видео до конца, сначала вперёд от позиции, затем назад.
6. Следующая запись: префикс звука, в видеорежиме — индекс и первый интервал видео.

Одновременно не больше двух запросов. Фоновые запросы идут с подсказкой скорости.
Срочный запрос прерывает фоновый поток. При выходе из видеорежима загрузка уровней 4–5
останавливается, уже загруженное остаётся до смены записи.

- **Решение:** принята рекомендация (владелец, 27.11.2026).

### T03. Окно по времени, а не по байтам

Из индекса (`stss`, `stsz`, `stco`/`co64`, `stts`) вычисляется диапазон байтов отрезка
`[t − 10, t + 10]`. Начало сдвигается к предыдущему ключевому кадру. Звуковые куски
внутри диапазона маленькие, отдельно их не вырезаем. Разбор индекса уже есть
в `video-stream.ts` и `audio-mp4.ts` через mp4box. При интервале до 10,25 с окно
захватывает минимум один целый интервал перед позицией.

- **Решение:** принята рекомендация (владелец, 27.11.2026).

### T04. Поведение ClipVideo

- Убрать `hold` при открытии и перемотке (P02 Б). Звук ставит на паузу только пользователь.
- После первого кадра не скрывать видео. При перемотке остаётся последний кадр до нового.
- До первого кадра показывать обложку записи, затем плавно перейти к видео за 150 мс.
- «Загружаем видеоряд…» показывать только при отсутствии кадра больше 1,5 с.
- Рассинхрон после перемотки исправлять переходом к ключевому кадру в загруженных
  байтах и ускорением `playbackRate`, как уже делает `clipPlaybackRate`.
- **Решение:** принята рекомендация (владелец, 27.11.2026).

### T05. Полоса загрузки в видеорежиме

Загруженные байты видео переводятся во временные отрезки по индексу. Полоса
в видеорежиме — пересечение отрезков звука и видео (P03). В звуковом режиме полоса
остаётся прежней.

- **Решение:** принята рекомендация (владелец, 27.11.2026).

### T06. Хранение и замеры

- Видео текущей записи хранится в памяти вкладки страницами по 64 КиБ, как звук (P04 А).
  Предыдущая запись очищается при смене. Бюджет одной записи — 256 МиБ. Сверх него
  удаляются страницы дальше всего от позиции. Самое крупное видео на проде — 205 МБ,
  оно помещается целиком.
- Метки `performance.mark` для клика, первого байта, `loadedmetadata`, первого кадра,
  паузы звука и перемотки. Сводка выводится в консоль по флагу
  `localStorage.hibikiPlaybackDebug`. По ней владелец сделает замер в своём Chrome.
- **Решение:** принята рекомендация (владелец, 27.11.2026).

### T07. Что учесть

- В Safari и Firefox ретранслятор работает с сервис-воркером. Без него остаётся
  обычный `src`, как сейчас.
- Длинные интервалы между ключевыми кадрами: перемотка назад в загруженное стоит до
  0,3 с декодирования. Последний кадр закрывает эту паузу.
- Под Kaname ответы медиа идут с `private, no-store`. Хранение в памяти вкладки
  на время сессии этому не противоречит.
- На сервере диск занят на 97 %, свободно 1,8 ГБ. Задача серверного места не занимает.
  Нужно отдельное решение владельца.
- Необязательно: виртуальный файл только с видеодорожкой `/files/:id/video`.
  Он убирает повторную загрузку звука в видео (3–8 % трафика). Отложить до замеров T06.

### Границы реализации

- Новый загрузчик обслуживает исходный MP4 со звуком (своё и по ссылке) — это все
  346 видео на проде. Видеоряд, назначенный записи (`/api/items/:id/visual/:rev`),
  не передаёт размер и индекс. На проде таких назначений нет. Он остаётся на родной
  загрузке, но получает новое поведение ClipVideo.
- Видео без звуковой дорожки, где ведущим служит сам `<video>`, остаётся на прежнем
  пути с `video-stream.ts`.
