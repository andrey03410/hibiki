# Правила плейлистов

## Контракт и вычисление

`packages/contracts/src/index.ts` экспортирует `Rule`, `PlaylistDefinition`,
`ruleSchema`, `playlistDefinitionSchema`. Документ:
`{version:1, rule, sort:'source'|'title'|'newest'|'duration'|'last-started', manualOrder?:string[]}`.

| Правило | Значение |
|---|---|
| `{type:'items', ids:[…]}` | Ручные items в указанном порядке |
| `{type:'playlist', id}` | Текущий результат другого плейлиста |
| `{type:'tag', id}` | Все items с тегом |
| `{type:'filter', kind?, local?, minDuration?, maxDuration?}` | Фильтр библиотеки |
| `{type:'favorite'}` | Избранные записи |
| `{type:'history', condition, count?, days?}` | Ещё не слушал/не дослушал, минимум быстрых пропусков, давно не включал |
| `{type:'union', rules:[…]}` | Объединение |
| `{type:'intersection', rules:[…]}` | Пересечение |
| `{type:'difference', include, exclude}` | Явные исключения |

Старое правило тега выбирает его точные назначения, в том числе после архивирования.
В правиле источника `descendants: true` включает активные дочерние узлы.
У композиции с несколькими подходящими путями сохраняется одна позиция.

Один результат свободно смешивает audio/video. `local=true` означает доступный
локальный источник владельца медиатеки. `local=false` выбирает записи без
такого источника. Неизвестная длительность не проходит заданные границы min/max.

`packages/core/src/playlists.ts` экспортирует `collectReferences`,
`validatePlaylist` → `{valid,issues}`, `resolvePlaylist` →
`{items,reasons,excluded,total,duration}`. Resolver бросает ошибку при невалидных
правилах; `library.ts` превращает её в `invalid_playlist` и HTTP 422.
Длительность результата — сумма известных секунд. Причины включения/исключения
на русском доступны сайту и MCP.

## Семантика и бюджеты

Дубли ID убираются. Явные исключения побеждают повторное включение через union
и ссылку на плейлист. Исключения внутри вычитаемого выражения не протекают наружу:
`A − (B − C)` сохраняет C, если C было в A. Источники и manualOrder задают
стабильный порядок; title/newest/duration сохраняют порядок при равенстве,
неизвестные длительности идут последними. Порядок вложенного плейлиста учитывается.

Схемы строго запрещают неизвестные поля и исполняемые правила. Лимиты одного AST:
глубина 20, 500 узлов, 10 000 item-ссылок, сериализованный документ до 262 144
символов. manualOrder — до 10 000 ID. Проверка до рекурсивного Zod-разбора защищает
от слишком глубоких/циклических объектов.

Validator проверяет существование всех ссылок в библиотеке владельца, включая
manualOrder, прямые и косвенные циклы при замене плейлиста. Раскрытие зависимостей
ограничено глубиной 40 и 10 000 узлов. При удалении зависимостей сервис сообщает,
какие плейлисты их используют, вместо молчаливого повреждения правил.

Проверка графа и сохранение выполняются в одной транзакции с tx-aware snapshot:
два конкурентных сохранения не обходят запрет циклов.

Состав пересчитывается по свежей библиотеке при resolve/preview. Начатая очередь —
снимок ID; изменения правил не переставляют текущие треки. Очередь и shuffle —
в `packages/core/src/queue.ts` и [web](web.md).

`history` получает закрытую сводку владельца, не возвращает счётчики в составе
результата. `last-started-before` не включает записи без запусков; сортировка
`last-started` ставит такие записи последними. Связь с YouTube материализует состав
в обычный список ID; базу меняет сервис синхронизации, не общий редактор правил.
При вложении подборка с личными правилами передаёт только свой итоговый набор,
не исключения за его пределами. Для Bearer/MCP у такого графа также скрываются
причины и списки исключённых записей.

## Каталог, редактор и состав

`GET /api/library/overview?playlists=summary` отдаёт метаданные карточек, `trackCount`
и небольшой массив `coverUrls`. Запрос без параметра сохраняет полные определения
для клиентов предыдущих версий. Карточки появляются по готовому обзору. Неизвестный
счётчик отображается чертой, а при отсутствии изображения видна заставка.
Браузер запрашивает по одной обложке за раз для карточки рядом с видимой областью.
Название ведёт на страницу подборки. Для владельца `GET /api/playlists/:id/detail` одним ответом возвращает метаданные, вычисленный состав и признак зависимости от истории. При ручном списке вычисление читает записи, упомянутые в правиле и ручном порядке. Первый ответ включает порядок ID и подробные сведения о первых 24 записях. При прокрутке страница догружает до 100 записей за раз. Маркер версии, граница времени правил истории и текущие права защищают от устаревшего состава. Плеер и ручная перестановка используют полный порядок. Исключённые записи открываются по запросу.

Обложка открывает редактор по `/playlists/:id?edit=1`. При прямом переходе метаданные загружаются отдельно, и состав страницы не задерживает форму. Кнопка «Поделиться» доступна в каталоге и на странице своего плейлиста. Каталог сохраняет текущую очередь при любом из этих действий. Компактный API `GET /api/playlists/:id/playback` сохраняет прежний контракт для клиентов.

Триггеры SQLite в миграции `20261123170000_playlist_counts` отмечают владельца
в `PlaylistCountWork` при изменении медиатеки, правил или значимых полей сводки
прослушивания. Worker проверяет заявки раз в три секунды. Он применяет общий resolver
к одному снимку владельца и публикует до трёх изображений из результата.
Он использует миниатюры YouTube по ID и проверяет локальные файлы до первой
декодируемой обложки в подборке.
Счётчики, изображения и упорядоченные ID публикуются в одной транзакции после
проверки версии и срока заявки. Публикация сохраняет ревизию и время правки подборки.

Миграция `20261123180000_playlist_playback` ставит существующие плейлисты на расчёт.
Запуск и доступ по ссылке используют `LibraryService.playlistIds`. Сохранённые
ID действуют при совпадении версии и до ближайшей границы правил истории.
Пока идёт перерасчёт, сервис вычисляет порядок тем же resolver по сокращённой
проекции медиатеки. Результат переиспользуется до смены версии владельца или
границы правил истории. Триггер меняет маркер при каждом росте версии, поэтому
после отката транзакции другая правка с тем же номером получает свой результат.
При открытии по ссылке проверяются актуальный состав и наличие собственных
источников у записей исходной подборки. Повреждённое или слишком глубокое правило
оставляет счётчик неизвестным у затронутых подборок. При ошибке работы с БД фоновый повтор
запланирован через минуту. Изменения сводки при отсутствии правил истории
перерасчёт не запускают.

## Как проверить

`packages/contracts/src/index.test.ts`, `packages/core/src/playlists.test.ts`
покрывают композицию, порядок, дубли, глобальные исключения, вложенную разность,
неизвестные/чужие ID, циклы и раздувание графа. `library.test.ts` проверяет тот же
путь через сервис и БД. В `library-pages.test.ts` проверяются ожидающий и
готовый счётчики в каталоге, обложки, ограниченный ответ старта, назначения тегов,
изменение истории, точная граница времени и публикация при конкурентной правке.

Вживую собрать через UI/MCP «плейлист ∪ тег ∪ item − исключения», проверить причины,
затем изменить дочерний список и обновить состав. Проверить смешанное audio/video
воспроизведение и сохранение уже запущенной очереди.
